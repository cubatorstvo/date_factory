# DATE FACTORY — технический план реализации

**Статус:** верхнеуровневый план реализации  
**Назначение:** определить модули проекта, их границы, зависимости и рекомендуемый порядок разработки  
**Источник продуктовых требований:** `docs/MASTER_GDD.md`  
**Важно:** этот документ НЕ является подробной технической спецификацией отдельных систем.

---

# 1. Правило работы с этим планом

Проект реализуется последовательно отдельными модулями.

Для каждого модуля перед началом реализации должна появиться отдельная спецификация с конкретными требованиями.

Cursor НЕ должен:

- самостоятельно детализировать отсутствующие механики;
- придумывать правила, которых нет в `MASTER_GDD.md` или отдельной спецификации модуля;
- реализовывать будущие модули заранее;
- создавать универсальные системы «на будущее» без необходимости;
- переносить старую архитектуру из donor только потому, что она уже существует;
- связывать модули сильнее, чем требуется текущей задачей.

Если модуль ещё не проработан отдельно, он может существовать только в виде минимального интерфейса/заглушки, если это необходимо уже реализуемому модулю.

Donor используется согласно отдельному Project Rule и остаётся read-only.

Игра должна состоять из небольших независимых систем с понятной ответственностью.

Старая архитектура v1 не является шаблоном для новой версии.

# 3. Порядок реализации

---

## MODULE 00 — Project Foundation

Базовая структура нового Godot-проекта.

Включает:

- структуру каталогов;
- базовые project settings;
- input actions;
- минимальные глобальные сервисы;
- правила зависимостей между модулями;
- базовую debug-инфраструктуру;
- подключение необходимых общих компонентов из donor.

**Зависимости:** нет.

---

## MODULE 01 — Player FPS Core

Базовое управление игроком от первого лица.

Включает:

- движение;
- камеру;
- коллизии;
- взаимодействие с миром;
- общий интерфейс interactable-объектов;
- базовые переходы между состояниями управления игроком и UI/мини-играми.

**Зависимости:** MODULE 00.

---

## MODULE 02 — Core Game State

Единое минимальное состояние прохождения.

Включает основные постоянные данные:

- текущая стадия;
- Деньги;
- Авторитет;
- Опытность;
- Баллы прокачки;
- характеристики героя;
- отношения с девушками;
- открытые локации;
- сюжетные флаги;
- поздние показатели клонов.

Модуль хранит данные, но не реализует правила конкретных механик.

**Зависимости:** MODULE 00.

---

## MODULE 03 — Content Data Layer

Data-driven описание игрового контента.

Включает структуры данных для:

- девушек;
- самцов;
- черт;
- тегов;
- свиданий;
- событий;
- перков;
- состязаний;
- сюжетных стадий;
- локаций;
- наград и требований.

Контент должен добавляться данными, а не размножением отдельных систем.

**Зависимости:** MODULE 00, MODULE 02.

---

## MODULE 04 — Character Framework

Единая система персонажей.

Включает:

- базовую мужскую модель;
- базовую женскую модель;
- конфигурацию внешности;
- одежду;
- волосы;
- аксессуары;
- анимационные состояния;
- простую идентификацию конкретного NPC;
- размещение персонажей в мире.

Не включает механику свиданий или состязаний.

**Зависимости:** MODULE 01, MODULE 03.

---

## MODULE 05 — Progression & Perks

Общая система развития героя.

Включает:

- характеристики Мышца / Внешность / Капитал / Аура;
- получение и расход Баллов прокачки;
- дерево/ветки перков;
- требования перков;
- эффекты уже купленных перков;
- предоставление эффектов другим игровым системам через простой публичный интерфейс.

**Зависимости:** MODULE 02, MODULE 03.

---

## MODULE 06 — Rival Encounter Framework

Общая система взаимодействия с самцами-соперниками.

Включает:

- право на вызов;
- проверку Авторитета;
- инициатора конфликта;
- выбор типа состязания;
- запуск мини-игры;
- результат победы/поражения;
- изменение Авторитета;
- реакцию и уход проигравшего NPC;
- поддержку сюжетных и обычных соперников.

**Зависимости:** MODULE 02, MODULE 03, MODULE 04, MODULE 05.

---

## MODULE 07 — Rival Minigames

Набор конкретных мужских состязаний как отдельных подмодулей общего Rival Framework.

Подмодули:

- 07A — Пощёчинный бой;
- 07B — Танцевальное противостояние;
- 07C — Сигма-давление;
- 07D — Денежное противостояние.

Все мини-игры используют единый контракт запуска и возврата результата.

**Зависимости:** MODULE 06.

---

## MODULE 08 — Girl Discovery & Phone Journal

Система поиска и знакомства с девушками до свидания.

Включает:

- фиксированные ситуации девушек в городе;
- попытку знакомства;
- требования по Опытности;
- получение номера;
- повторную попытку через игровое время;
- список контактов;
- журнал известной информации о девушке.

Не включает само свидание.

**Зависимости:** MODULE 02, MODULE 03, MODULE 04.

---

## MODULE 09 — Dating Core

Основная системная логика свидания.

Включает:

- запуск свидания;
- приветствие как информационный этап;
- выбор трёх центральных событий;
- запрет трёх событий одной категории;
- запрет повторения одного конкретного события за вечер;
- категории Разговор / Событие пространства / Предложение;
- варианты действий;
- теги действий;
- основную черту девушки;
- дополнительную черту свидания;
- итоговую оценку каждого действия;
- прощание;
- итог свидания.

Модуль не должен быть привязан к конкретной девушке.

**Зависимости:** MODULE 03, MODULE 04, MODULE 05, MODULE 08.

---

## MODULE 10 — Relationships & Girl Completion

Прогресс отношений с конкретными девушками.

Включает:

- накопление отношений;
- порог +5;
- повторные свидания;
- фиксацию успешно покорённой девушки;
- +1 Опытность;
- начисление Баллов прокачки;
- предотвращение повторного получения основной награды.

**Зависимости:** MODULE 02, MODULE 08, MODULE 09.

---

## MODULE 11 — Story / Stage Framework

Лёгкая система сюжетной последовательности.

Включает:

- стадии прохождения;
- цели стадии;
- сюжетную девушку стадии;
- сюжетного соперника;
- подквесты;
- открытие следующей стадии;
- разблокировку новых участков мира и правил.

Система должна быть простой и сценарной, без универсального сложного quest engine.

**Зависимости:** MODULE 02, MODULE 03, MODULE 06, MODULE 10.

---

## MODULE 12 — World & Location Framework

Физический мир игры и управление доступом к локациям.

Основные зоны:

- квартира;
- городской хаб;
- кафе / ресторан;
- качалка;
- пространство Внешности;
- зарплатная шахта;
- лаборатория;
- поздние производственные помещения;
- финальная локация.

Включает:

- загрузку/переходы;
- стадийные ограничения доступа;
- точки размещения NPC;
- точки сюжетных событий;
- интерактивные объекты.

**Зависимости:** MODULE 01, MODULE 04, MODULE 11.

---

## MODULE 13 — Salary Mine & Money Loop

Полная мужская экономическая линия.

Включает:

- зависимость денежного уровня от Авторитета;
- раннее получение зарплаты через шахту;
- развитие дохода;
- антигринд-переход к пассивному доходу;
- использование Денег другими системами.

Не включает позднюю экономику клонов.

**Зависимости:** MODULE 02, MODULE 06, MODULE 11, MODULE 12.

---

## MODULE 14 — Stage Content: Manual Game

Наполнение ручной части игры реальным контентом.

Сюда входят:

- сюжетные девушки до лаборатории;
- сюжетные соперники;
- обычные девушки;
- обычные самцы;
- наборы dating events;
- игровые ситуации знакомства;
- staged scenes;
- стадийные открытия мира;
- связанные интерактивные объекты.

Это контентный модуль поверх уже готовых систем, а не новая архитектура.

**Зависимости:** MODULE 07, MODULE 10, MODULE 11, MODULE 12, MODULE 13.

---

## MODULE 15 — Media / Attention Escalation

Медийная стадия героя.

Включает:

- сюжетную медийную сцену;
- журнал / газету / новости;
- фотосессию;
- расширение телефона;
- возможность публиковать фотографии;
- входящие инициативы девушек;
- визуальное ощущение растущей известности;
- переход к перегрузке свиданиями.

**Зависимости:** MODULE 10, MODULE 11, MODULE 12, MODULE 14.

---

## MODULE 16 — Dating Overload

Системное создание ощущения, что ручного героя больше не хватает.

Включает:

- поток входящих свиданий;
- ограниченную физическую возможность героя присутствовать лично;
- рост невыполненного спроса;
- сюжетный триггер необходимости клонирования.

Модуль служит мостом между ручной и инкрементальной частью.

**Зависимости:** MODULE 15.

---

## MODULE 17 — First Clone Sequence

Первое клонирование как отдельная сюжетная механика.

Включает:

- открытие лаборатории;
- сцену первого клона;
- мини-игру создания клона;
- появление первого физического дубля;
- первый выбор: отправить клона работать или на свидания.

**Зависимости:** MODULE 11, MODULE 12, MODULE 16.

---

## MODULE 18 — Clone Incremental Core

Поздняя инкрементальная система.

Основные показатели:

- всего клонов;
- клоны на работе;
- клоны на свиданиях;
- Деньги в единицу времени;
- Свидания в единицу времени.

Включает:

- производство клонов;

- пассивное начисление результатов;
- инкрементальные улучшения;
- компьютерный интерфейс управления.

Никаких индивидуальных протоколов или QA каждого клона.

**Зависимости:** MODULE 02, MODULE 13, MODULE 17.

---

## MODULE 19 — Physical Clone Visualization

Физическое представление первых клонов в FPS-мире.

Включает:

- ограниченное число визуальных слотов свиданий;
- физические клоны в первых рабочих/романтических помещениях;

- переход от индивидуально видимых клонов к абстрактным массовым числам;
- визуальный уход массовых клонов «в мир».

Не является отдельной симуляцией каждого клона.

Финальный рост масштабов перед концовкой.

# 6. Приоритет простоты

Для любого модуля действует правило:

> Реализовать минимальную систему, которая полностью выполняет утверждённый дизайн.

Не требуется:

- универсальность для несуществующего будущего контента;
- сложная event-driven архитектура ради архитектуры;
- enterprise-паттерны;
- отдельные менеджеры для каждого маленького понятия;
- симуляция того, что игрок не видит;
- совместимость с отменённой v1;
- автоматическое сохранение старых механик.

Если задачу можно решить небольшой локальной системой без ущерба для GDD, это предпочтительнее.

---

# 7. Приоритет разработки

При конфликте между задачами порядок приоритета:

1. Рабочий игровой цикл.
2. Отсутствие блокирующих ошибок.
3. Понятность происходящего игроку.
4. Комедийная подача.
5. Скорость производства контента.
6. Визуальный polish.
7. Архитектурная универсальность.

---

# 8. Правило завершения модуля

Модуль считается завершённым только когда:

- его утверждённая отдельная спецификация выполнена;
- он реально работает в игре;
- основные сценарии проверены;
- отсутствуют очевидные legacy-зависимости;
- он не требует будущего модуля для проверки своей основной функции;
- документация отражает фактическое состояние.

После этого переходить к следующему модулю.
