# 6. Приоритет простоты

Для любого модуля действует правило:

> Реализовать минимальную систему, которая полностью выполняет утверждённый дизайн.

Не требуется:

- универсальность для несуществующего будущего контента;
- сложная event-driven архитектура ради архитектуры;
- enterprise-паттерны;
- отдельные менеджеры для каждого маленького понятия;
- симуляция того, что игрок не видит;
- совместимость с отменённой v1;
- автоматическое сохранение старых механик.

Если задачу можно решить небольшой локальной системой без ущерба для GDD, это предпочтительнее.

# 7. Приоритет разработки

При конфликте между задачами порядок приоритета:

1. Рабочий игровой цикл.
2. Отсутствие блокирующих ошибок.
3. Понятность происходящего игроку.
4. Комедийная подача.
5. Скорость производства контента.
6. Визуальный polish.
7. Архитектурная универсальность.

---

# 8. Правило завершения модуля

Модуль считается завершённым только когда:

- его утверждённая отдельная спецификация выполнена;
- он реально работает в игре;
- основные сценарии проверены;
- отсутствуют очевидные legacy-зависимости;
- он не требует будущего модуля для проверки своей основной функции;
- документация отражает фактическое состояние.

После этого переходить к следующему модулю.
