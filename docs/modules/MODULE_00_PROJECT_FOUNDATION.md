# MODULE 00 — PROJECT FOUNDATION

**Проект:** Date Factory  
**Модуль:** 00 — Project Foundation  
**Статус:** обязательная спецификация перед реализацией  
**Назначение:** подготовить чистую техническую основу нового проекта без реализации игровых механик  
**Продуктовый источник истины:** `docs/MASTER_GDD.md`  
**Верхнеуровневый технический план:** `docs/TECHNICAL_IMPLEMENTATION_PLAN_RU.md`

---

# 1. Цель модуля

Создать минимальную, чистую и автономную основу нового Date Factory, на которой следующие модули можно реализовывать последовательно без наследования архитектуры отменённой версии игры.

После завершения MODULE 00 проект должен:

- корректно открываться в Godot;
- корректно запускаться через основную сцену;
- иметь понятную базовую структуру;
- иметь заранее зафиксированные правила размещения будущего кода и контента;
- иметь базовый Input Map;
- иметь минимальную debug-инфраструктуру;
- быть полностью независимым от donor-проекта во время выполнения;
- не содержать никакой реализации будущих игровых механик;
- не содержать legacy-архитектуру старой Date Factory;
- быть готовым к отдельной реализации MODULE 01 — Player FPS Core.

MODULE 00 — это фундамент, а не первый gameplay prototype.

## 2.1. Что Cursor НЕ имеет права решать самостоятельно

Cursor не должен самостоятельно придумывать:

- игровые механики;
- правила прогрессии;
- дополнительные ресурсы;
- новые характеристики;
- новые названия продуктовых сущностей;
- поведение игрока;
- поведение NPC;
- структуру свиданий;
- механику самцов;
- механику девушек;
- квестовую систему;
- стадии;
- логику денег;
- логику Авторитета;
- логику Опытности;
- логику Баллов прокачки;
- механику клонов;
- UI-flow будущих систем;
- дополнительные gameplay-сервисы «на будущее».

Если для текущей задачи неожиданно требуется продуктово-геймдизайнерское решение, которого нет в документации, Cursor должен НЕ додумывать его.

Он должен:

1. проверить `MASTER_GDD.md`;
2. проверить текущую спецификацию модуля;
3. проверить последние явные инструкции пользователя;
4. если ответа всё ещё нет — остановить именно эту часть работы и явно сформулировать вопрос пользователю.

## 2.2. Что Cursor МОЖЕТ и ДОЛЖЕН решать самостоятельно

Чисто технические решения являются ответственностью Cursor.

Примеры:

- конкретный тип Godot Node для технического контейнера;
- нужен ли конкретному техническому helper `RefCounted`, `Node`, `Resource` или другой подход;
- как лучше оформить небольшой debug helper;
- нужны ли typed variables в конкретном месте;
- как безопаснее организовать загрузку конфигурации;
- какой layout использовать для минимальной технической сцены;
- какой способ проверки ошибок является наиболее уместным;
- какие Project Settings разумны для desktop-проекта;
- какие generic donor-файлы действительно стоит переиспользовать;
- какие технические helper-файлы стоит объединить или разделить.

Но техническое решение нельзя принимать по принципу «первое, что пришло в голову».

Перед реализацией нетривиального технического решения Cursor должен:

1. понять фактическую задачу;
2. проверить текущую структуру проекта;
3. при необходимости посмотреть соответствующую реализацию в donor как reference;
4. рассмотреть разумные варианты реализации;
5. выбрать вариант, соответствующий актуальным Godot best practices;
6. учитывать реальный масштаб Date Factory: маленькая одиночная indie-игра, которую нужно быстро производить;
7. предпочесть самый простой вариант, который остаётся чистым, понятным и расширяемым для уже утверждённых следующих модулей;
8. не строить enterprise-архитектуру;
9. не строить инфраструктуру для гипотетических будущих требований;
10. зафиксировать существенное техническое решение в `docs/TECHNICAL_DECISIONS.md`.

Если два решения одинаково корректны, выбирать более простое.

# 6. Архитектурный принцип проекта

Новая Date Factory — небольшая single-player игра.

Архитектура должна оптимизироваться под:

- скорость разработки;
- понятность;
- локальность изменений;
- лёгкое добавление контента;
- отсутствие скрытых зависимостей;
- возможность Cursor понимать один модуль без чтения всей кодовой базы.

Не оптимизировать под:

- multiplayer;
- modding;
- live service;
- DLC framework;
- network replication;
- server authority;
- generic RPG framework;
- generic quest engine;
- generic dialogue engine;
- сложный dependency injection;
- service locator;
- universal event bus;
- plugin architecture для gameplay;
- поддержку старой версии игры.

# 11. Dependency rules

С самого начала соблюдать следующие правила.

## 11.1. Donor dependency

Ни один runtime-файл не может ссылаться на:

```text
../date_factory_legacy
```

---

## 11.2. UI dependency

Gameplay/domain logic не должна зависеть от UI.

UI позже может читать состояние и вызывать публичные gameplay-команды, но игровая логика не должна существовать внутри кнопок/панелей.

---

## 11.3. Assets dependency

Asset-файлы не являются владельцами gameplay logic.

Не размещать domain systems внутри импортированных asset-папок.

---

## 11.4. Feature locality

Код конкретной механики должен находиться рядом с этой механикой, а не в глобальном helper-файле.

---

## 11.5. No universal event bus

Не использовать глобальную шину событий как стандартный способ связи всех систем.

Для локальной связи использовать обычные Godot references/signals/calls согласно best practices и фактической задаче.

---

## 11.6. No circular dependency

Не создавать циклические зависимости между крупными feature-модулями.

Если такая зависимость начинает возникать, сначала пересмотреть ответственность модулей.

---

## 12.2. Файлы и GDScript

Использовать один последовательный стиль именования, соответствующий Godot/GDScript conventions текущей версии.

Cursor самостоятельно выбирает технически корректный convention, но:

- не использовать бессмысленные сокращения;
- не использовать имена `Manager` без реальной managerial responsibility;
- не использовать `Helper` как свалку разнородных функций;
- не использовать `Utils` для feature-specific logic;
- имя файла должно объяснять ответственность.

---

## 12.3. Nodes

Node names должны быть читаемыми и описывать роль узла.

Не использовать:

- `Node2`;
- `Thing`;
- `Manager2`;
- `TempFinal`;
- `NewNew`;
- и подобные временные имена в committed implementation.

# 15. Rendering baseline

На этом этапе не фиксировать окончательный художественный pipeline.

Текущая стратегия проекта:

> визуал временно собирается из имеющихся ассетов; окончательный art direction не является задачей MODULE 00.

Поэтому:

- не строить специальную toon-render систему;
- не писать custom post-processing framework;
- не внедрять сложные shader pipelines;
- не менять глобальный rendering architecture ради предполагаемого будущего стиля.

Нужен только стабильный современный baseline, позволяющий работать с 3D-ассетами.

# 16. Debug infrastructure

Создать минимальную техническую debug-инфраструктуру.

Она должна позволять:

- различать обычный debug log;
- warning;
- error;
- быстро понимать, какой модуль сообщает проблему;
- отключать избыточные debug-сообщения в release build либо не генерировать их там;
- не скрывать реальные Godot errors.

Точный технический подход Cursor выбирает сам после анализа best practices.

Не создавать:

- сложную logging framework;
- telemetry;
- analytics;
- remote logging;
- debug console с командами;
- developer cheats;
- on-screen inspector.

Если достаточно одного небольшого helper или стандартных Godot средств — использовать их.

---

# 17. Error handling

Общие правила:

- ошибки разработки не должны молча игнорироваться;
- невозможные состояния должны быть заметны в debug;
- не использовать `null`-проверки как способ скрыть неправильную архитектуру;
- не писать десятки fallback-путей ради того, чтобы ошибка «не падала»;
- не ловить и не маскировать проблемы, которые должны быть исправлены.

Для пользовательских runtime-ситуаций обработка будет определяться соответствующими модулями позже.

# 18. GDScript quality baseline

Cursor должен использовать актуальный GDScript и best practices текущей версии Godot.

Ожидания:

- понятные типы там, где они улучшают надёжность и читаемость;
- небольшие scripts с одной понятной ответственностью;
- явные публичные интерфейсы;
- минимум hidden side effects;
- минимум глобального mutable state;
- отсутствие копипасты, если уже существует очевидная общая техническая реализация;
- отсутствие generic abstraction до появления хотя бы реального повторяющегося паттерна;
- комментарии объясняют `why`, а не пересказывают очевидный код.

Не создавать архитектурные абстракции только ради «чистоты».

# 19. Third-party addons

Проверить, какие addons уже присутствуют в новом проекте или реально нужны из donor.

Правило:

- addon разрешён, если он прямо облегчает текущую разработку;
- addon не переносится только потому, что был в legacy;
- gameplay проекта не должен становиться зависимым от тяжёлого plugin framework без необходимости.

Для каждого сохранённого/перенесённого addon кратко зафиксировать:

- название;
- назначение;
- почему нужен;
- влияет ли он на runtime или только editor.

Записать это в `TECHNICAL_DECISIONS.md` или `PROJECT_STRUCTURE.md`.
